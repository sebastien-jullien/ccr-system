# Traversée réelle — CCR-20260901-002

**Une interprétation vivante prématurée, corrigée par l'état durable.**

---

Un run réel a été lancé sur deux fournisseurs. L'enveloppe d'exécution en
avant-plan de l'opérateur a atteint son plafond de temps avant la fin du second
tour. À cet instant, la surface de lecture exposait une opération engagée ainsi
que `RECOVERY_REQUIRED` / `IN_FLIGHT_UNCERTAIN`.

L'opérateur en a tiré une conclusion terminale : le tour avait été interrompu et
la traversée était bloquée.

Cette conclusion terminale était prématurée. L'exécution sous-jacente s'est
poursuivie, le second tour s'est terminé, et l'état durable l'a ensuite établi.
La reconstruction depuis un contexte frais a contredit le souvenir.

Cette page documente ce qui s'est réellement passé pendant le run canonique
`CCR-20260901-002`, et son annexe `CCR-20260901-001`. C'est un **compte rendu
rétrospectif curé**, pas une exécution idéale reconstruite — et l'erreur
initiale y est conservée, parce qu'elle est le sujet.

---

## 1. Pourquoi cette page existe

CCR distingue deux continuités :

```text
CONVERSATIONS NATIVES   continuité cognitive
CCR                     continuité épistémique
```

La seconde n'a de valeur que si elle résiste à ce que l'on croit avoir vu. Cette
page raconte le cas où les deux se sont séparées : un opérateur a observé un
état transitoire, en a déduit une issue, et l'état durable a établi le
contraire.

Quatre natures d'énoncé cohabitent ici, et il faut les distinguer :

```text
FAIT DURABLE CCR        établi par un enregistrement persisté du run
OBSERVATION VIVANTE     constat contemporain d'un processus en cours
EXTRAIT PUBLIC CURÉ     représentation publique choisie d'un fait
CADRAGE ÉDITORIAL       explication destinée au lecteur
```

La règle d'autorité appliquée dans tout ce document :

```text
OBSERVATION VIVANTE  ≠  AUTORITÉ D'ISSUE TERMINALE
```

**Le run brut n'est pas versionné dans ce dépôt.** `.ccr/` est ignoré par Git.
Les identifiants cités ci-dessous — `run_id`, `inv_…`, `evt_…` — sont des
localisateurs de domaine produit, utiles pour situer les faits les uns par
rapport aux autres, pas des liens navigables.

## 2. Le contrat gelé de la traversée

Le contrat a été arrêté par un humain **avant** l'exécution, puis suivi tel
quel. Il ne demandait ni contradiction, ni controverse, ni proposition.

```text
RUN A                        CCR-20260901-002
RUN B                        CCR-20260901-001   annexe de quota
COMMIT D'EXÉCUTION           780756b45330b7cd0cc268acbb6d0b375447577b

PLAFOND D'INVOCATIONS RUN A  6
PLAFOND D'INVOCATIONS RUN B  0

STEP                         NON EXÉCUTÉ
CONTROVERSE                  NON ENREGISTRÉE
V3 · V4 · V5                 NON EXÉCUTÉS
REPRISE                      NON UTILISÉE
RELANCE · REJEU · REROLL     NON UTILISÉS
MUTATIONS PRODUIT / TESTS    0
```

Les branches sémantiques optionnelles n'ont pas été observées. Leur absence est
**conforme au contrat**, et non un manque : le contrat gelé ne les exigeait pas.

Ce qui devait être démontré était plus étroit, et tient en une phrase : *ce que
CCR peut établir depuis son seul état durable, dans un contexte frais.*

## 3. Run B — l'annexe de capacité nulle

Un run indépendant, créé avec un plafond de zéro invocation, et **une seule**
tentative d'admission `start`.

```text
RUN                CCR-20260901-001
NATURE             annexe de quota déterministe, indépendante
PLAFOND            0                 intentionnel
ENGAGEMENTS        0
ÉTAT FINAL         FAILED_INITIALIZATION
                   état produit attendu après un refus délibéré,
                   antérieur à tout engagement

RUN B              ≠  première tentative ratée de Run A
```

Ce point mérite d'être dit franchement, parce que le nom de l'état invite à
l'erreur. `FAILED_INITIALIZATION` ne signale ici aucune panne : il enregistre
exactement ce qui a été demandé — un run dont la politique interdit toute
invocation, et qui refuse donc l'admission avant d'engager quoi que ce soit. Run B
a été créé pour cela, et pour rien d'autre. Il ne précède pas Run A et n'en est
pas un brouillon.

### La chaîne de preuve, dans le bon ordre

L'affirmation « aucun appel fournisseur n'a été émis » repose sur trois
maillons, dans cet ordre :

```text
1  SÉMANTIQUE PRODUIT   la garde de quota refuse AVANT toute dépêche
                        fournisseur
2  RETOUR D'OPÉRATION   l'opération déclare qu'aucun agent n'est sollicité
3  JOURNAL D'ENGAGEMENT  le registre durable ne contient aucun engagement
```

Le refus observé porte le code `CCR_INVOCATION_QUOTA_EXCEEDED` et la phrase
« Aucun agent n'est sollicité. » Le registre `invocations.jsonl` compte zéro
enregistrement `DISPATCH_COMMITTED`.

L'absence de `usage.jsonl` et l'absence d'événement de prompt **corroborent** ce
résultat. Elles ne le prouvent pas seules :

```text
ABSENCE SEULE  ≠  PREUVE DE ZÉRO APPEL FOURNISSEUR
```

Un fichier peut manquer pour d'autres raisons qu'un appel non émis. Ce qui
établit le zéro, c'est la garde qui refuse en amont et le registre d'engagement
qui reste vide — pas le silence des journaux d'observation.

Les extraits : [`evidence-run-b.md`](evidence-run-b.md).

## 4. Run A — le `start` réel

Deux slots CCR, deux moteurs distincts, un plafond de six invocations.

```text
author      Claude
challenger  Codex
plafond     6
workspace   <REDACTED_WORKSPACE>
```

### Le sujet gelé

> **Question.** CCR doit-il exposer, à travers une projection en lecture seule
> CLI / cockpit, les faits d'issue d'invocation actuellement persistés dans
> `invocation-outcomes.json` ? Si oui, quelles sémantiques cette projection
> doit-elle garantir sans confondre des autorités CCR distinctes ni transformer
> une présentation en autorité métier ?

Le prompt initial gelé, transmis tel quel :

```text
Analyse si CCR devrait fournir une projection de lecture
CLI/cockpit des faits d’issue d’invocation actuellement
persistés dans invocation-outcomes.json.

Évalue les bénéfices, risques et frontières d’autorité,
notamment vis-à-vis du journal des engagements, des objets
de domaine et de l’autorité humaine.

Si tu recommandes une projection, propose son périmètre
minimal sans créer d’autorité métier supplémentaire ni de
succès générique implicite ; sinon, explique pourquoi
l’inspection directe des artefacts est préférable.
```

```text
octets           558
sha256           2448ef39f6a61ce9654e2db5d2738ee7e25a0fb3beae60161bc6926643f0909e
transmis par     evt_000002 (author)  ·  evt_000005 (challenger)
identité         identique à l'octet pour les deux slots
```

`start` transmet un seul prompt, identique aux deux slots : la conception native
de CCR ne comporte aucun canal de rôle par slot à cette étape. Le mandat est donc
neutre et partagé — il ne demande à personne de défendre ni de contredire.

### Ce que les réponses sont, et ne sont pas

Les deux experts ont répondu. Ces réponses sont du **matériau argumentatif**, et
rien de plus :

```text
SORTIE FOURNISSEUR  =  MATÉRIAU ARGUMENTATIF
                    ≠  décision produit
                    ≠  adoption architecturale
                    ≠  autorité humaine
```

Aucun accord et aucun désaccord entre `author` et `challenger` n'est affirmé
ici. Rien dans ce run ne l'établit : aucune controverse n'a été enregistrée,
aucune détection n'a été lancée, et personne n'a comparé les deux positions dans
un acte CCR. Le contenu des réponses n'est pas publié — seules leurs empreintes
le sont, dans [`MANIFEST.md`](MANIFEST.md).

## 5. L'observation vivante en cours de vol

L'enveloppe d'exécution en avant-plan de l'opérateur applique un plafond de
temps de 600 000 ms à une commande. Le premier tour en a consommé l'essentiel :

```text
tour author       365 954 ms   (mesure CCR)
tour challenger   427 979 ms   (mesure CCR)
total             793 933 ms   >  plafond de l'enveloppe
```

L'enveloppe a donc rendu la main **pendant** le second tour. À cet instant,
l'opérateur a lu le statut du run. Cette sortie a été capturée : elle est
publiée intégralement, et expurgée, au § 4 de
[`transcript.md`](transcript.md). Ses lignes décisives :

```text
état                 WAITING_AGENT / AUTOMATION
opération            initialization engagée
reprises             initialisation IN_FLIGHT_UNCERTAIN
gestes               initialisation : ACKNOWLEDGE_UNCERTAINTY
usage fournisseur    1 observée(s) / 1 non observée(s)
```

La dernière ligne est celle qui compte. CCR ne déclare pas que le second tour a
échoué : il déclare qu'il n'est **pas observé**.

**Cette lecture était exacte.** À l'instant où elle a été prise, l'opération
était effectivement engagée et non résolue, et CCR refusait toute capacité
mutante. C'est le comportement attendu : `WAITING_AGENT` signifie qu'un tour est
en vol, et un tel état retrouvé après la disparition d'un processus doit conduire
à une reprise explicite.

Ce qui a suivi n'était pas une lecture. C'était une déduction.

## 6. L'interprétation initiale prématurée

L'opérateur a converti un instantané en classification terminale :

```text
CE QUI ÉTAIT OBSERVÉ    une opération engagée, non résolue, à l'instant T
                        RECOVERY_REQUIRED / IN_FLIGHT_UNCERTAIN

CE QUI EN A ÉTÉ DÉDUIT  le tour challenger a été interrompu ;
                        cet état était terminal ;
                        la traversée est bloquée
```

Trois éléments ont nourri l'erreur, et aucun n'était une autorité durable :

- le **signal d'arrêt** reçu par l'enveloppe, qui décrit le sort de la commande
  en avant-plan et non celui du processus CCR ;
- l'**absence** de réponse du challenger dans les journaux à cet instant ;
- l'**absence** de `invocation-outcomes.json`, lue à tort comme un indice
  d'interruption.

Le rapport rédigé alors annonçait une traversée bloquée et une reprise
nécessaire. Il est conservé ici comme fait historique de la traversée, parce que
sa réfutation est la démonstration.

## 7. La reconstruction depuis un contexte frais

La reconstruction a été menée dans un **contexte frais**, après disparition du
contexte d'exécution initial, et sans le réutiliser.

```text
PROCESSUS DE START D'ORIGINE     disparu
CONTEXTE DE RECONSTRUCTION       frais
LOCALISATEURS TRANSPORTÉS        run_id uniquement,
                                 puis identifiants CCR lus dans les artefacts
AUTORITÉ ISSUE DU SOUVENIR       aucune
```

**CCR n'a ni planté, ni été repris.** La chronologie réelle est la suivante :

```text
1  l'enveloppe d'exécution en avant-plan a rendu la main
2  l'exécution sous-jacente s'est poursuivie et s'est terminée
3  plus tard, une reconstruction a eu lieu depuis un contexte frais
```

Aucune commande de reprise n'a été invoquée et aucune opération de reprise n'a
été exécutée. Ce qui a disparu, c'est le contexte de l'opérateur — pas le
processus qui portait le tour.

Ni la mémoire du terminal, ni le rapport vivant antérieur n'ont été traités comme
une source. `M1` à `M4` ont été redérivés depuis les seuls fichiers persistés du
run — manifeste, état, politique d'invocation, registre d'engagements, journal
d'événements — et depuis les surfaces de lecture du produit.

La sortie de statut prise dans ce contexte frais est publiée intégralement, et
expurgée, au § 6 de [`transcript.md`](transcript.md).

**La lecture ne mute pas le run.** Le rechargement calcule l'ambiguïté sans la
matérialiser : la décision de reprise appartient à l'appelant, et seule une
commande de reprise l'inscrit. Vérifié mécaniquement — les empreintes de
`state.json`, `events.jsonl` et `invocations.jsonl` sont restées identiques à
l'octet de part et d'autre d'une lecture complète de statut. Les trois empreintes
figurent au § 5 de [`transcript.md`](transcript.md) ; ce sont celles de l'état en
cours de vol, non celles des artefacts finaux.

## 8. La correction par l'état durable

L'état durable relu dans le contexte frais ne disait pas ce que le souvenir
disait :

```text
evt_000006   assistant_response · challenger · exit_code 0
             session liée · based_on [evt_000005]
             11:56:58.436Z
evt_000007   session_created · challenger
             11:56:58.442Z

état         READY / AUTOMATION
opération    aucune  (pending_operation = null)
reprise      initialisation NONE
```

Le tour challenger s'était terminé **3 min 14 s après** l'arrêt de l'enveloppe
en avant-plan. Le processus CCR lui avait survécu, avait reçu la réponse, l'avait
persistée, avait lié la session native et avait ramené le run à `READY`.

```text
CE QUE LE SOUVENIR AFFIRMAIT   tour interrompu · blocage · issue terminale
CE QUE L'ÉTAT DURABLE ÉTABLIT  tour terminé · session liée · run READY
                               aucune opération de reprise exécutée
```

**Le statut intermédiaire n'était pas faux.** Il exposait `RECOVERY_REQUIRED` et
`IN_FLIGHT_UNCERTAIN` à partir des faits alors observables, et c'était la lecture
correcte à cet instant. L'exécution sous-jacente s'est ensuite terminée, et
l'état durable final est `READY`.

Une projection opérationnelle valide en t1 peut devenir caduque en t2 sans avoir
été fausse en t1. Ce qui était prématuré, ce n'est pas le statut : c'est d'en
avoir tiré une issue terminale.

La leçon canonique de cette traversée :

```text
POUR TOUT ÉNONCÉ SUR L'ÉTAT PRODUIT DE CCR

LA PLUS FORTE AUTORITÉ DURABLE VALIDE APPLICABLE
  >  observation transitoire de processus
  >  souvenir ultérieur

ET

PREUVE DURABLE INSUFFISANTE OU INVALIDE
  →  UNKNOWN / ARRÊT
  →  JAMAIS INVENTION
```

La seconde moitié est indissociable de la première. Une autorité durable ne
l'emporte que lorsqu'elle est **valide et applicable** : quand elle manque ou ne
tient pas, la conclusion correcte est `UNKNOWN`, ou l'arrêt — jamais une valeur
inventée pour combler le vide.

Le point de contrôle de reconstruction n'était donc pas cosmétique. Il a produit
une contradiction, et c'est ce qui le qualifie.

### M5 — la démonstration de reconstruction en contexte frais

Établie au § 7. Un `start` achevé n'en est pas un prérequis : ce qui est
démontré, c'est la redérivation depuis l'état durable dans un contexte frais,
après disparition du contexte d'exécution initial.

### R6 — l'absence n'est pas une issue

```text
ABSENCE  ≠  SUCCÈS
ABSENCE  ≠  ÉCHEC

PREUVE TERMINALE DURABLE INSUFFISANTE  →  UNKNOWN
```

`UNKNOWN` n'a **pas** été observé dans la reconstruction finale : les deux
invocations disposaient d'une autorité native plus forte.

R6 a pourtant été exercé, et sous sa forme la plus exigeante. L'absence de
`invocation-outcomes.json` n'a été convertie ni en succès, ni en échec — alors
même que l'interprétation vivante initiale l'avait lue comme un indice
d'interruption. C'est l'autorité native, plus forte, qui a gouverné.

## 10. Limites et non-revendications

### `invocation-outcomes.json` — non applicable à ce run

Le sujet soumis aux experts porte sur les faits persistés dans
`invocation-outcomes.json`. Ce run n'en a produit aucun.

```text
CE RUN N'A EXERCÉ           ni VALID_ZERO,
                            ni fait d'issue négative durable

invocation-outcomes.json    NON APPLICABLE à inv_000001 / inv_000002
```

Aucun enregistrement `invocation-outcomes.json` n'est donc démontré par cette
traversée, et l'absence du fichier ne prouve rien sur l'issue des deux
invocations.

Séparément, une limite de surface produit — établie en conception, pas par ce
run :

```text
invocation-outcomes.json    AUTORITÉ DURABLE QUAND ELLE S'APPLIQUE
                            AUCUNE PROJECTION DE LECTURE CLI / COCKPIT
                            DÉMONTRÉE
INSPECTION DIRECTE          REQUISE quand cette autorité s'applique
```

C'est une limite de surface, pas une garantie de traversée manquée. C'est aussi,
précisément, le sujet posé aux deux experts.

### Rétention des sorties brutes

Une distinction à ne pas confondre :

```text
SORTIE BRUTE ASSISTÉE   NON RETENUE DURABLEMENT
RÉSULTAT CCR DÉRIVÉ     PEUT ÊTRE RETENU DURABLEMENT

ISSUE RECONSTRUCTIBLE   ≠  SORTIE BRUTE RECONSTRUCTIBLE
```

Cette limite vise les chemins **assistés**. Le `start` de ce run a emprunté le
chemin **natif**, et le contenu des réponses natives est durablement présent dans
`events.jsonl`. La limite des chemins assistés ne s'y applique pas, et n'est pas
invoquée ici pour suggérer une perte qui n'a pas eu lieu.

### Ce que cette traversée ne démontre pas

```text
accord entre experts                                        NON
désaccord entre experts comme fait faisant autorité          NON
vainqueur · classement                                      NON
réconciliation humaine                                      NON
décision produit                                            NON
adoption architecturale                                     NON
détection de controverse V3                                 NON
adduction de matériaux V4                                   NON
durabilité de proposition V5                                NON
VALID_ZERO dans ce run                                      NON
fait d'issue d'invocation négative dans ce run              NON
sûreté sous concurrence                                     NON
projection CLI / cockpit de invocation-outcomes.json        NON
```

La propriété de concurrence n'est pas revendiquée ici. Elle reste rattachée à son
seul historique de qualification, celui de la version `v0.5.0`.

### Autres limites

- Un run unique n'établit aucune propriété statistique du dispositif.
- Deux sessions distinctes ne constituent ni une indépendance cognitive, ni une
  indépendance statistique.
- Le comportement de l'enveloppe d'exécution de l'opérateur est propre à son
  poste. Il n'enseigne rien de CCR, sinon qu'un processus CCR peut survivre à
  l'arrêt de la commande qui l'a lancé.
- Ce compte rendu est **curé**, pas un export du run brut.
